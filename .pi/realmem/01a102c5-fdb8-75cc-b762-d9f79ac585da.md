A release is an annotated tag `vX.Y.Z` (its message becomes the release description). The workspace Cargo.toml version must match, and the install commands in README.md, scripts/install.sh and docs/webjet-operations-guide.md name the tag (Forgejo has no "latest" download URL). Version bump checklist: Cargo.toml version, `cargo update -w`, and install refs in README.md / scripts/install.sh / docs/webjet-operations-guide.md. Since commit 2cca64d (2026-10), `fuzz/Cargo.lock` is gitignored and not committed: it used to go stale with every version bump or dependency change in the crates the fuzz workspace uses (e.g. v0.8.0 bump, socket2 added to webjetd), making CI's `cargo test --locked --manifest-path fuzz/Cargo.toml` fail with "cannot update the lock file … because --locked was passed". Now `scripts/fuzz-lock.sh` copies the main `Cargo.lock` to `fuzz/Cargo.lock`, so the fuzz targets use the same dependency versions (cargo prunes what the fuzz workspace doesn't use and adds only what it has on its own). ci.yml's fuzz smoke/clippy steps, fuzz.yml (`scripts/fuzz-lock.sh && cd fuzz && cargo +nightly fuzz build -O`) and scripts/fuzz.sh run it first, and the fuzz steps no longer pass `--locked`. Locally: `scripts/fuzz-lock.sh && cargo test --release --manifest-path fuzz/Cargo.toml --no-default-features`. The version-bump checklist no longer needs `cargo update --manifest-path fuzz/Cargo.toml -w` nor committing fuzz/Cargo.lock.

Published on forgejo.wolf109909.top/webj8/webjet (public repo): v0.4.1, v0.4.2 and v0.4.3 exist, each with 22 files (CI-built Linux/Windows files plus macOS files uploaded from the Mac). The release pages and downloads for v0.1.0–v0.4.0 were deleted (API `DELETE /api/v1/repos/webj8/webjet/releases/{id}`); their git tags remain. Consequences: `webjetup install v0.3.0` etc. fail with "no such release", and `RELEASE=vX.Y.Z` release checks (`docker/release-test.sh`, `docker/runbook-test.sh`) only work for v0.4.1 and later. v0.4.3 (commit c1b3355): control socket moved to /var/run/webjet, launchd plist captures stdout, `webjetup status` fixes; passed `docker/webjetup-test.sh` before tagging and `WEBJET_TEST_DNS=1.1.1.1 docker/release-test.sh v0.4.3` after publishing (Debian 11, Ubuntu 20.04, Debian 12; amd64 and arm64). Release flow: bump version → webjetup-test → commit, tag with the notes as the message, push → CI release job (about 15 min) → `scripts/release.sh vX --targets "<macOS targets>"` builds, then `--publish` uploads into the CI-made release once it exists → release-test.

Releases come from CI. Pushing the tag runs `.forgejo/workflows/release.yml` on the user's Forgejo runner (label `ubuntu-latest`; runner vp309-gpuserver on root@10.1.1.22, docker-in-docker setup in /root/docker/forgejo-runner, `force_pull: true`, jobs get no Docker socket) with every job in the builder image `forgejo.wolf109909.top/webj8/webjet-builder:2` (`ci/builder.Dockerfile`, public package linked to the repo, about 6 GB). release.yml runs the tests, re-fetches the annotated tag (actions/checkout drops it), then `scripts/release.sh <tag> --publish --targets` for x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu and x86_64-pc-windows-msvc. There is no `RELEASE_TOKEN` secret; the workflow's automatic token is enough to create the release and upload assets (v0.3.0: jobs `test` and `release` succeeded, 14 assets: Linux x86_64/aarch64 tar.gz, Windows zip, webjetup for the three targets, install.sh, each with .sha256). macOS isn't built in CI: the user adds it from a Mac with `scripts/release.sh vX.Y.Z --publish --targets "aarch64-apple-darwin x86_64-apple-darwin"`, which uploads into the existing release and replaces same-name assets. `ci.yml` (push/PR/workflow_dispatch): fmt, clippy `-D warnings` for Linux (with and without default features) and Windows, tests incl. the fuzz workspace; webjet-app excluded. This Forgejo (16.0.5) has no API to re-run a workflow run; use workflow_dispatch or push. The image is built and pushed by hand (docs/development.md: bump the tag in ci.yml and release.yml); on the runner box build it inside the dind daemon (`docker exec -i docker_dind docker -H tcp://127.0.0.1:2375 build ... -`) with `--build-arg http(s)_proxy=http://192.168.31.199:7890`. That proxy returns 502 for forgejo.wolf109909.top, so the box's dind service and runner job envs have forgejo.wolf109909.top in NO_PROXY (backups of the old compose/runner config next to them, suffix .bak-20261004035110). Don't name a build arg XWIN_VERSION: cargo-xwin reads that env var as the MSVC version.

Builder image: rust:1-bullseye (glibc 2.31); gcc-aarch64-linux-gnu cross toolchain (linker/CC/CXX/AR env vars, bindgen `--sysroot=/usr/aarch64-linux-gnu`); LLVM from apt.llvm.org (bullseye), trimmed to clang, clang-cl, lld-link, llvm-lib, llvm-dlltool and libclang (LIBCLANG_PATH=/opt/llvm/lib, needs libtinfo5); nasm and ninja-build (cargo-xwin uses the Ninja CMake generator; BoringSSL/aws-lc need NASM for Windows); Kitware CMake 3.31; Node 20 for actions/checkout; cargo-xwin 0.23.1 with the Microsoft CRT and SDK pre-downloaded (`cargo xwin cache xwin`, XWIN_CACHE_DIR=/opt/xwin). Clang >= 19 is required because Microsoft's C++ headers from cargo-xwin fail with STL1000 on older Clang, and `clang` must be on PATH (`/usr/lib/llvm-20/bin`) or bindgen in boring-sys can't find stddef.h. Debian's LLVM packages lack clang-cl/lld-link/llvm-lib/llvm-dlltool, so the Dockerfile links them to clang/lld/llvm-ar (they switch mode by name).

`scripts/release.sh <tag> [--publish] [--targets "…"]` checks tag == HEAD, clean sources and the version, then per target builds macOS natively (Mac only), Linux with cargo on Linux or in Docker via `docker/release.Dockerfile` elsewhere, and Windows with cargo-xwin. Output in `dist/<tag>/` (gitignored): `webjet-<tag>-<target>.tar.gz` (webjetd and webjetctl; before 0.3.0 also webjet-root and webjet-signer), the Windows `.zip` with the four .exe files, wintun.dll 0.14.1 amd64 (download checksum pinned) and wintun-LICENSE.txt, `webjetup-<tag>-<target>[.exe]` and `install.sh`, each with a `.sha256`. `--publish` needs WEBJET_FORGEJO_TOKEN (API and repo from the origin remote, or WEBJET_FORGEJO_API / WEBJET_FORGEJO_REPO); it pushes the tag if missing, creates or reuses the release and uploads.

Debian 11 build quirks (handled in docker/release.Dockerfile and the builder image): the archived security mirror no longer serves every update (drop the security lines; on amd64 libclang pulls libc6-i386 and friends pinned to unavailable versions, replaced by empty stub packages); Debian's CMake 3.18 is older than BoringSSL's minimum 3.22, so Kitware's CMake is used.
