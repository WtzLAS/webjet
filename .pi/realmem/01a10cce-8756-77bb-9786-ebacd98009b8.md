Two latency/metrics bugs fixed after 0.5.1:
1. `crates/webjet-net/src/kcp.rs` `run_session` only called `kcp.update()`, which flushes every 10 ms interval. That added up to ~10 ms per direction per hop, and delayed acknowledgements inflated KCP's RTT: a loopback KCP hop showed 17 ms against 0.3 ms for TLS. Fix: call `kcp.flush()` right after `kcp.send` or `kcp.input` (`flush_now`), and batch-drain `rx` (up to 64 datagrams) so one flush answers them all. Result: 0.6 ms hop RTT. Also BBR `on_delivery(.., app_limited)`: app-limited samples may raise the bandwidth estimate but never lower it. Test: `kcp::tests::small_messages_are_not_delayed` (median echo < 4 ms; about 21 ms without the flush).
2. `crates/webjetd/src/e2e.rs`: the PROBE handler echoed `reply.truncate(64)`, but an encoded `wp::Probe` is 66 bytes. Every PROBE_ACK failed to decode, so circuits were never measured (rtt 0, probes 0, loss → 1, `cost()` infinite, path choice blind, `paths.rs` closed "dead" circuits). Now `PROBE_ECHO_MAX = 128`; test `e2e::tests::probe_survives_echo`.
`metrics.rs` `build_report` now fills `RouteMetrics.e2e` (it was always None) via `route_e2e` (source circuits only; selected 0/1/2, session path_switches). Exposition adds `webjet_route_selected` and `webjet_route_path_switches_total`.
To diagnose: `webjetctl --socket /tmp/webjet-local/node-02/control.sock --json local sessions` shows each circuit's probes, rtt and loss.
