The CLI was merged in 0.3.0 (user decision: dedicated `root` group, clean break, no compatibility wrappers):
- `webjetd`: only `run` and `signer` (was `webjet-signer`; `--key`, `--socket`), plus hidden Windows `service` (the service manager entry point). `webjetd init/enroll/install/uninstall` are gone.
- `webjetctl`: `init --genesis [--config --data-dir]` (was `webjetd init`), `enroll <string> [--config --data-dir]` (was `webjetd enroll`; works on a bootstrap controller while its agent runs), the node and admin commands as before, and `root --dir … <cmd>` = the old `webjet-root` (code in `crates/webjet-tools/src/root.rs`, `RootCmd`, run with `spawn_blocking`). `agent_config()` in webjetctl.rs loads webjetd.toml for init/enroll via `Config::override_data_dir`.
- `webjetup` owns the Windows service: `sc.exe create webjetd binPath= "\"…\webjetd.exe\" --config \"…\" service" start= auto depend= W32Time/Dnscache`, plus description and failure actions; removal does `sc.exe delete` and clears NRPT rules with comment `webjet`. It enrolls with `webjetctl enroll --config …`, or `webjetd --config … enroll` when the installed version is before 0.3.0 (`layout::before_0_3`), and deletes the retired `webjet-root`/`webjet-signer` binaries on install/remove (`RETIRED_PROGRAMS`).
- Release archives contain webjetd and webjetctl only (plus wintun.dll on Windows); `PROGRAMS = ["webjetd", "webjetctl"]`.
- Docker: entrypoint runs `webjetctl init`/`webjetctl enroll` on first start; the signer container command is `webjetd signer --socket … --key …`.
