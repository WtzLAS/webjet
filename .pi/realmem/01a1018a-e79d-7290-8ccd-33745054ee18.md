Deadlocks were the most common Webjet agent bug (found by running real traffic, diagnosed with macOS `sample <pid>` — look for `lock_slow`). Rules: never call a helper that takes a lock while holding a lock it may take — clone, drop guard, then call (`Node::records`, `Node::hops`, `Node::circuits`, store, e2e session `inner`; e.g. `transport::priority` locks records, so `endpoint_addrs` must clone the record first; `e2e::Sessions::in_progress` iterates all sessions so compute it before locking one). In Rust edition 2024, a temporary in an `if let` / let-chain condition (e.g. a `MutexGuard` from `n.circuits.lock()`) lives until the end of the whole `if`, including its body — `cargo clippy --fix` collapsing nested ifs into let-chains caused a deadlock in webjetd's e2e re-key (`... && let Some(c) = n.circuits.lock().local_circuits(..).next() && let Err(e) = start_handshake(..)` held the circuit lock while `LocalCircuit::send` took it again; it fired only after the 120 s re-key timer; `scripts/soak-test.sh` — local net 200+ s, checks every control socket answers — catches this class). Fix: bind with `let x = ...lock()...;` first, then test. `Node::store` is a `StoreLock` wrapper whose `read()` is `read_recursive()` because nested reads happened everywhere and a queued writer deadlocked a fair RwLock. Never hold parking_lot guards across `.await`. Controller `apply_committed` and snapshot install share `apply_lock`.
