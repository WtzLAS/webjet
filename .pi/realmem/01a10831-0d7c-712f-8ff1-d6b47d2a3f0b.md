On macOS the root volume is sealed and read-only, so `/run` does not exist and even root cannot create it. Up to 0.4.2, webjetd, webjetctl and webjet-app defaulted to `/run/webjet/control.sock`. On a Mac the agent then ran without a control socket (`webjetctl local status`: "connect to /run/webjet/control.sock: No such file or directory"). The launchd plist only captured stderr, but tracing logs go to stdout, so the bind error was lost.

Fixed after 0.4.2:
- `webjetd::ipc::default_control()` / `default_signer()` are `/var/run/webjet/control.sock` and `/var/run/webjet/signer.sock` on every Unix. On Linux `/var/run` is a symlink to `/run`.
- These are the single source of the default: webjetctl's `--socket` (`default_value_os_t`), `webjetd signer --socket`, and webjet-app's `client::default_socket` all use them. Never write the literal path anywhere else.
- webjetup's `launchd_plist` sets both StandardOutPath and StandardErrorPath to `/var/log/webjetd.log`. `setup_service` rewrites an existing plist when its content differs.
- `webjetup status` prints `enrolled unknown` when it can't read the root-only state dir, instead of a wrong "no". On 0.4+ it queries the agent with `webjetctl --json local status`; it used to call the pre-0.4 `status` subcommand.

Docker still passes `/run/webjet/...` explicitly through `WEBJET_SOCKET`/`WEBJET_CONFIG`. That is fine on Linux.

Workaround for an installed 0.4.2 Mac: add `control_socket = "/var/run/webjet/control.sock"` to `/Library/Application Support/Webjet/webjetd.toml`, run `sudo launchctl kickstart -k system/net.webjet.webjetd`, then `sudo webjetctl --socket /var/run/webjet/control.sock local status`.
