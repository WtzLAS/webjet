Reverse proxy feature (added after 0.5.1, Linux only for ingress and real-IP targets):
- Rules: `[[proxy]]` in node-scope config (`webjetctl local config`), wire `NodeConfig.proxy: [ProxyRule]` {name, protocol 6/17, listen_port, target [one IP | selectors], target_port, real_ip=true}. Validated by `webjet_core::proxy::rules` (also in statemachine `set_node_config`; data role required). TOML in webjet-tools config.rs `ProxyFile`.
- Ingress: iptables chain `WEBJET-PROXY` (nat PREROUTING DNAT listen ports → proxy address = overlay resolver IP; filter/mangle FORWARD accept + TCPMSS). `crates/webjetd/src/proxy.rs` `Proxy::from_client` picks target (address via `Dataplane::route`, selectors via rendezvous hash `proxy::rank`), rewrites, sends e2e frame type `ftype::PROXY = 9`.
- Target: `[proxy] accept_real_ip = true` in webjetd.toml → mangle `WEBJET-REALIP`/`WEBJET-REALIP-OUT`, connmark 0x574a0000/0xffff0000, ip rule → table 22346 default dev tun, rp_filter=2; advertises EndpointRecord feature `proxy-real-ip` (all new nodes advertise `proxy`). Otherwise ingress SNATs to its overlay IP, ports 61000–65535. Targets behind gateways are always SNAT'd; real_ip=true there gives a rule warning + `proxy_rule` alarm (user asked for this warning).
- Separation: own `proxy::Table` (separate Conntrack), not counted in tun_rx/tun_tx/conntrack; control call `proxy` / `webjetctl local proxy`; `MetricReport.proxy: [ProxyMetrics]` → `webjet_proxy_*` families; webjet-app Connections tab has an "overlay flows / reverse proxy" switch (fixture node-02.json has a `proxy` key; it is written with json indent=1, sort_keys, ensure_ascii).
- Tested by docker/e2e.sh (real IP to node-b, UDP by selector with SNAT, two rules to a LAN host behind gw, removal clears the capture). In the test containers the config is at `$WEBJET_CONFIG` (/run/webjet/webjetd.toml), not /etc/webjet.
