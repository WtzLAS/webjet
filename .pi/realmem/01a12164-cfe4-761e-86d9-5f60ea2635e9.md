Bug found after v0.11.2 (user's GMod server in Docker on Fedora CoreOS target 10.4.0.6, ingress idc.wolf109909.top): with `accept_real_ip`, a server in a container (Docker -p DNAT, bridge MTU 1500) behind a real-IP target hung at "retrieving server info". Cause: tun MTU 1280; replies > 1280 make the host send the container ICMP frag-needed, which is RELATED to the marked conntrack, so `WEBJET-REALIP-OUT` (mangle OUTPUT) copied the connmark onto it and table 22346 routed it into webjet0 → the container never learned PMTU, all big replies lost. Fix in `platform::proxy_real_ip` (crates/webjetd/src/platform.rs): the MARK rule adds `-m conntrack --ctdir REPLY`. Hot-patch: `iptables -t mangle -R WEBJET-REALIP-OUT 1 -m connmark --mark 0x574a0000/0xffff0000 -m conntrack --ctdir REPLY -j MARK --set-xmark 0x574a0000/0xffff0000`. Covered by step "4b" of docker/realip-test.sh (wjr-srv container on wjr-lan 10.99.0.0/24 behind node-b DNAT, replies 100–3000 B). Diagnose on a host: `nstat -az IpFragFails IcmpOutDestUnreachs`; container `ip route get <client>` shows `mtu 1280` in cache once PMTU works. Target host has dae (eBPF tproxy on br-steam) — not the cause.
