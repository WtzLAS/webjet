User decision (after 0.5.0): the webjetd control channel must be usable without root by `webjetctl` and `webjet-app`. Implementation in `crates/webjetd/src/ipc.rs`: `Listener::bind(path, Access)`. `Access::Everyone` (control channel, `control.rs serve`): Unix socket mode 0666, and when the socket is in the default dir (`/var/run/webjet`) the agent adds o+x to that dir at start, because older webjetup systemd units create it with RuntimeDirectoryMode=0750 (new units use 0751). On Windows the pipe uses SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x12008b;;;WD)`: everyone gets FILE_GENERIC_READ|FILE_WRITE_DATA but not FILE_APPEND_DATA (= FILE_CREATE_PIPE_INSTANCE). So `ipc::connect` opens the pipe with std OpenOptions access_mode GENERIC_READ|FILE_WRITE_DATA + FILE_FLAG_OVERLAPPED + SECURITY_IDENTIFICATION and wraps it with `NamedPipeClient::from_raw_handle`; tokio's ClientOptions asks for GENERIC_WRITE and would be denied. `Access::Private` (0600; SYSTEM+Administrators) is kept for `webjetd signer`'s socket. Rationale: every state change through the channel is signed (account/root/emergency), so the socket grants no rights; trade-off accepted: any local user can read the network map and conntrack. Docs updated: docs/configuration.md control_socket, docs/app.md, ops guide "Running webjetctl" (sudo only for `local init`/`local enroll`), architecture §19.5, README platform table. `docker/webjetup-test.sh` checks unprivileged `su wjuser -c "webjetctl local status"` works.

macOS: the root volume is sealed/read-only, so `/run` does not exist and even root cannot create it. Up to 0.4.2 the daemons defaulted to `/run/webjet/control.sock`, so on a Mac the agent ran without a control socket (`webjetctl local status`: "connect to ... No such file or directory"); the launchd plist only captured stderr while tracing logs go to stdout, so the bind error was lost. Fixed after 0.4.2: `webjetd::ipc::default_control()`/`default_signer()` return `/var/run/webjet/control.sock` and `/var/run/webjet/signer.sock` on every Unix (on Linux `/var/run` is a symlink to `/run`); these are the single source of the default — webjetctl `--socket` (`default_value_os_t`), `webjetd signer --socket`, webjet-app `client::default_socket` — never write the literal path elsewhere. webjetup `launchd_plist` sets both StandardOutPath and StandardErrorPath to `/var/log/webjetd.log`; `setup_service` rewrites an existing plist when content differs. `webjetup status` prints `enrolled unknown` when it can't read the root-only state dir (on 0.4+ it queries the agent via `webjetctl --json local status`; previously the pre-0.4 `status` subcommand). Docker still passes `/run/webjet/...` explicitly via `WEBJET_SOCKET`/`WEBJET_CONFIG` — fine on Linux. Workaround for installed 0.4.2 Mac: add `control_socket = "/var/run/webjet/control.sock"` to `/Library/Application Support/Webjet/webjetd.toml`, `sudo launchctl kickstart -k system/net.webjet.webjetd`, then `sudo webjetctl --socket /var/run/webjet/control.sock local status`.
