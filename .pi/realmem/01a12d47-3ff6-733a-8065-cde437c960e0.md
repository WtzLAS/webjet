Since commit f9a5000, relay frame buffers have this layout.

**Sending: `Hop::send_relay(flow, record)`** (`crates/webjetd/src/node.rs`)
- The buffer must start with `hop::RECORD_HEADER` (4) bytes of room, followed by the relay frame.
- `webjet_net::hop::seal_record(rec::RELAY, &mut buf)` writes `type[1] || len[3]` into that room. Nothing is copied.
- Callers:
  - `circuit::LocalCircuit::send` builds `[0;4] + relay_header + frame`.
  - Transit forwarding reuses the buffer the frame arrived in.

**Receiving**
- The stream reader uses `hop::read_record_buf`. It returns the whole record, header included, so the payload is `buf[4..]`.
- The reader calls `circuit::on_relay_record` (frame at offset 4).
- Lane frames, which have no record header, and tests call `circuit::on_relay_frame` (offset 0).
- Both go to `on_relay(n, hop, buf, at)`.
  - Transit frames rewrite the relay header at `buf[4..]`. When `at == 0` they first `splice` 4 bytes in front.
  - Local frames go to `e2e::on_frame(buf, at + RELAY_HEADER)`.

**Rules**
- The writer, `on_lane`, `TestHopRx::relay()` and `RELAY_ECN_OFFSET` (= 4 + 4) all still assume `Out::Relay.frame` is a full encoded record.
- Never pass a bare frame to `send_relay`: it would lose its first 4 bytes.

Tests: `hop::tests::records_built_in_place_match_encoded_ones` and `a_record_read_whole_keeps_its_header`.
