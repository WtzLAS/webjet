Commit 45ae630 (after 0.12.1, not released/tagged): hole punching between two symmetric NATs and failed-dial rejection.
- `crates/webjetd/src/punch.rs` `should_try`: only "no direct UDP hop yet" + KcpFecTls priority != 0 on both sides; NAT types no longer matter (symmetric/symmetric is punched). `should_predict`: peer symmetric, whatever ours is (both-side prediction). Retry schedule unchanged (15 s doubling to 5 min, immediately on RecordsChanged/HopDown).
- `Attempt.rejected: Vec<SocketAddr>`: `reject()` runs when the dial to a validated (PONG) address fails (e.g. another webjet node at the same private IP on our LAN — two LANs sharing 192.168.1.0/24). Ignores stale dials (`validated != Some(addr)`), drops the address from `theirs`, and within WINDOW (6 s since `started`) resets validated/dialing so the next PONG is nominated; after the window calls `finish` with failure. Rejected addresses are ignored by on_check (ping & pong). Offers drop candidates equal to our own `my_candidates`. `punch::status` JSON shows `rejected`.
- Docs: architecture §11.7 (port prediction, "Symmetric NAT on both sides", "Wrong answers" bullets); removed "Port prediction for symmetric NAT" from rejected alternatives. webjet-app model.rs nat_text for symmetric changed.
- Test pitfall: on the user's Mac, 192.168.1.x routes via utun6 (VPN), so `nat::dialable` rejects it in unit tests; use documentation addresses 203.0.113.x / 198.51.100.x for punch test candidates.

This supersedes the v0.7.0 (d081161) punch.rs rules "peer symmetric and we aren't" for prediction and the cone-NAT-only implicit scope; the OFFER/GO check window (6 s, 50 ms then 200 ms), peer-reflexive learning, first-PONG nomination, id-ordered dialing and retry/backoff on RecordsChanged/HopDown still apply, as do nat.rs tunnel detection/`[nat]` config, kcp.rs K_PUNCH PING/PONG token protocol, and `transport::nat_type` counting only RELAY-hop observations.
