`crates/webjetd/src/keystore.rs` `keychain::imp` fixes the 0.4.0 macOS keychain ACL bug. `store` creates the generic-password item (svce/acct/labl) via `SecKeychainItemCreateFromContent`; initial `SecAccess` from `SecAccessCreate`, then `SecACLSetContents(acl, NULL apps, …)` on every decrypt ACL from `SecAccessCopyMatchingACLList(kSecACLAuthorizationDecrypt)`. Result equals `security add-generic-password -A`: `applications: <null>`, no partition_id — webjetd reads without prompt even after upgrades. Before storing, any existing item is deleted by reference. `load`/`store`/`delete` run under `SecKeychain::disable_user_interaction()`; on -25308/-25293/-25243, `load` reports the item "doesn't let webjetd read it … can't be recovered" → re-key and enroll again. Items are deleted via `ItemSearchOptions` (`.keychains`, `.service`, `.load_refs(true)`, `Limit::All`) + `SecKeychainItemDelete` — works without read access; errSecItemNotFound (-25300) = none found. Dependencies (macOS-only, webjetd and webjetup): `security-framework-sys = "2"`, `core-foundation = "0.10"`. `webjetup nuke` calls `system::delete_keychain_items(sys, &l.config)` to delete items in the System keychain and in the keychain set by `[key] keychain` in webjetd.toml (parsed with toml); then verifies none are left, failing with the `security delete-generic-password` command otherwise. Tests use temporary keychains (`keychain_roundtrip` in webjetd, `nuke_deletes_keychain_items_it_cannot_read` in webjetup) with the `security` CLI as "other program". `security delete-generic-password` without UI also works on default-ACL items (verified). Inspect ACLs with `security dump-keychain -a /Library/Keychains/System.keychain`.
