`crates/webjet-release/src/http.rs` no longer uses `ureq::Proxy::try_from_env()`. `proxy_from()` reads `https_proxy`, `HTTPS_PROXY`, `all_proxy`, `ALL_PROXY`, `http_proxy`, `HTTP_PROXY` in that order (curl's order), plus `no_proxy`/`NO_PROXY`. It always builds the proxy with `resolve_target(false)`, so `socks5://` acts as `socks5h` and `socks4://` as `socks4a`. An invalid proxy URL makes every request fail (`Client.proxy_error`); it never falls back to a direct connection. Errors name the route ("connected via the SOCKS5 proxy H:P from all_proxy" / "directly"). A TLS certificate failure is Final, not retried, and carries a hint about interception and sudo dropping proxy variables.

The client itself is unchanged: ureq 3 + rustls (aws-lc-rs, classic kx only) with Mozilla webpki roots only. There is no OS trust store, so corporate/antivirus MITM CAs are never trusted.

Root cause of `invalid peer certificate: CaUsedAsEndEntity` reports behind SOCKS5 (2026-10): ureq 3 was built without its `socks-proxy` feature. A socks proxy from the environment was then silently ignored (only a `log::warn`), so webjetup connected directly and got an intercepted or self-signed cert. A manually configured socks proxy without the feature panics. Keep `socks-proxy` in the ureq features in `crates/webjet-release/Cargo.toml`. The test `requests_go_through_a_socks5_proxy_with_the_host_name` (fake SOCKS5 server, checks ATYP=domain) fails without it.

rustls-webpki checks the leaf's basicConstraints before the trust anchors. A CA:TRUE leaf (`openssl req -x509`, an interceptor, proxy or captive-portal cert) therefore gives CaUsedAsEndEntity instead of UnknownIssuer, which means the machine isn't talking to the real server. The real forgejo.wolf109909.top chain was fine on 2026-10-07: LE YE1 leaf CA:FALSE → Root YE → ISRG X2 → X1.

The remote upgrade helper (systemd/launchd service) has no proxy variables at all.
