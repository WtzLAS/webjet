macOS targets cross-compile on Linux in CI with `scripts/macos-cargo.sh <aarch64|x86_64>-apple-darwin <cargo args>`. On a Mac it is plain cargo; on Linux it needs `WEBJET_MACOS_SDK` (the CI image sets /opt/macos-sdk/MacOSX.sdk). It writes to ~/.cache/webjet-macos-tools:
- an `xcrun` shim (boring-sys runs `xcrun --show-sdk-path` for bindgen);
- symlinks `install_name_tool`/`otool`/`lipo` → llvm-* (CMake's Darwin platform files FATAL without install_name_tool);
- wrappers `<target>-clang`/`-clang++` = `clang --target=<arch>-apple-macosx<min> -isysroot SDK -fuse-ld=lld` (+ `-nostdinc++ -isystem SDK/usr/include/c++/v1` for C++). Without them CMake's compiler check links with GNU /usr/bin/ld ("unrecognised emulation mode: llvm").
It also sets SDKROOT and MACOSX_DEPLOYMENT_TARGET (11.0 arm64, 10.12 x86_64). ld64.lld signs arm64 ad hoc: the cross-built arm64 binaries pass `codesign -v` and run on the Mac.
Pitfall: SDK 27.0 (CLT for macOS 27) `.tbd` stubs list `arm64e.x1`, which LLVM 20's ld64.lld rejects ("could not load TAPI file … malformed file … unknown architecture"). The SDK packager (webjet-builder's scripts/macos-sdk.sh) therefore picks the newest SDK without `arm64e.x*` (26.5).
Building the image needs the Mac's proxy passed in as `http://host.docker.internal:7890`; without it DNS SERVFAILs. release.sh `build_macos` uses macos-cargo.sh (needs Darwin or WEBJET_MACOS_SDK). ci.yml has a `clippy (macOS)` step (aarch64), and release.yml builds all 6 targets.
